# Architecture Decision Log

**Status:** Approved design baseline; Milestone 1 implementation is in progress.

## Accepted design baseline
| ID | Decision | Rationale |
|---|---|---|
| D01 | Hybrid deterministic analysis and optional AI interpretation | Evidence plus richer explanation |
| D02 | One shared engine for CLI, GitHub Action, agents, web | Prevent drift and duplication |
| D03 | CLI + GitHub Action established the engine; the next delivery priority is local/self-hosted web over that same engine (D43) | Preserve standalone automation while improving the browser workflow |
| D04 | No mandatory persistent backend/database for CLI/Action | Local/self-hostable workflow |
| D05 | Project supports multiple repos and services | Real system architecture |
| D06 | Versioned, evidence-backed IR | Traceability and reusable generators |
| D07 | Confirm ambiguous cross-repo relationships | Avoid false claims |
| D08 | Type-specific deterministic diagram generators | Stable, valid output |
| D09 | Git-based docs and reviewable PR publication | Review, ownership, history |
| D10 | Modular monolith with replaceable boundaries | MVP simplicity, future flexibility |
| D11 | Language parsers separate from framework adapters | Extensibility |
| D12 | Initial ecosystems: Spring Boot, React, FastAPI | Focused deep support |
| D13 | AI-first preferred UX; no-key deterministic/local alternatives | Quality with choice |
| D14 | Agent-friendly noninteractive JSON CLI | Codex/Claude Code integration |
| D15 | System IR is a versioned JSON graph of nodes, edges, evidence, and claims | Portable, inspectable contract for all engine stages |
| D16 | Semantic identities are separate from source evidence and content hashes | Stable references without conflating identity, location, and bytes |
| D17 | Cross-repository relationships remain candidates until explicitly confirmed | Prevents inferred links from becoming authoritative silently |
| D18 | MVP AI providers are one cloud BYO provider and Ollama | AI remains central while keeping provider infrastructure replaceable |
| D19 | External AI requires explicit consent, redaction, and a local-only mode | Protects private repository content and preserves deterministic operation |
| D20 | Trusted built-in analyzers are Python modules; external analyzers use a versioned subprocess protocol | Fast MVP iteration with a language-neutral extension boundary |
| D21 | Generated documentation uses dedicated paths, a manifest, and fails on unexpected edits | Protects human-authored documentation from silent overwrites |
| D22 | Mermaid is the first diagram format for architecture/component and ERD; API documentation is Markdown | Limits rendering complexity while covering the MVP demo |
| D23 | Changes use full-project regeneration with no-op detection | Predictable output before incremental impact analysis exists |
| D24 | System documentation and documentation PRs use one coordination repository | Gives multi-repository publication one explicit ownership location |
| D25 | CLI output is versioned JSON with explicit exit codes; CI fails on unresolved required confirmations | Reliable automation and safe handling of ambiguity |
| D26 | Quality is evaluated with golden fixtures, precision/recall, provenance checks, and AI comparisons | Makes factual accuracy and AI contribution measurable |
| D27 | Development proceeds from contracts to one Spring Boot slice, then multi-repository AI-enhanced MVP | Controls risk without reducing the final MVP goal |
| D28 | RepoDocs is licensed under Apache 2.0 | Permissive adoption with an explicit patent grant |
| D29 | Repositories have a `source` or `destination` role with one explicit documentation destination; scans run in `local` or `pinned` snapshot mode, pinned requires an explicit pin, and evidence resolves to a commit or a content fingerprint (ADR-014) | Stable destination and provenance contracts before framework adapters build on the IR |
| D30 | Built-in analyzers implement a `detect`/`analyze` contract over a read-only, hash-checked repository context; evidence is `file` or `span` with line ranges; literal source facts are `observed` and name matches are `inferred`; unsupported constructs go into a required IR `limitations` list with a closed set of kinds; configuration values are never recorded (ADR-015) | Framework adapters share one boundary, keep evidence precise, and report what they cannot support instead of guessing |
| D31 | Front-end facts use `module`, `component`, `route`, and `http_request` nodes with `imports`, `references`, and `requests` edges; request sites are recorded only for literal URLs, with template holes preserved as `{expression}`; JSX element references resolve through imports and function calls never become relationships (ADR-016) | Gives correlation declared request targets and routes with evidence while keeping runtime behaviour out of the IR |
| D32 | Database facts use `database` and `table` nodes with `contains` and `references` edges read from SQL migrations and schema files; unsupported SQL, migration, and ORM constructs are reported as limitations; an entity and a table that share a declared name are linked by an `inferred` `maps_to` edge that names its basis and cites both sides (ADR-017) | Gives the data model and the later entity-relationship work an evidence-backed source without turning a name match into a fact |
| D33 | Cross-repository HTTP matches are always inferred candidates in a separate IR array; semantic IDs exclude evidence, revisions, and confidence; matching preserves competing endpoints and requires backend server evidence for an origin boost; OpenAPI inputs are bounded 3.0.x/3.1.x JSON with same-document references only, and persisted URLs omit userinfo, queries, and fragments (ADR-018) | Enables reviewable discovery without guessing service ownership or leaking URL secrets; confirmation and stale-state workflows remain in #18 |
| D34 | Candidate decisions are recorded noninteractively in a committed `repodocs.confirmations.json`, bound to the candidate's evidence and both snapshot revisions; a decision is stale when that evidence changes; every candidate requires a decision and `validate` exits with code 5 while any is unresolved or stale; confirmed candidates remain inferred (ADR-019) | Makes human authority explicit, reviewable, and tied to what was actually reviewed, and lets CI fail closed on new or changed links |
| D35 | AI providers receive only a deterministic, redacted evidence bundle built from the IR, with no source text; Anthropic (official SDK, optional extra) and Ollama share one provider protocol; external use requires recorded consent, otherwise the project is local-only; model claims are validated against the bundle, stored beside the IR with provider and model provenance, and are never `observed` (ADR-020) | Keeps deterministic extraction separate from AI, bounds what can leave the machine, and makes every accepted claim traceable to evidence |
| D36 | Current, revalidated AI claims render only into optional `architecture-ai.md`, never the deterministic overview, diagrams, or IR; stale/invalid AI inputs fall back to deterministic output with warnings; inferred claims require subject-bound evidence and multi-repository claims require an explicit confirmed candidate; golden fixtures measure bounded contribution, not general semantic truth (ADR-021) | Adds reviewable explanations with safe retirement, ownership protection, and no AI-created authority |
| D37 | Supported PostgreSQL tables and references produce deterministic Mermaid ER diagrams in `erd.mmd`; missing primary keys and unresolved relationships are reported in the diagram and documentation; Mermaid output passes documented renderer-compatible validation (ADR-022) | Completes the MVP diagram requirements with verified, editable relational models while preserving ownership and evidence |
| D38 | Generated documentation is published by `repodocs publish` as one commit on a bot-owned branch, only when it differs from the base and the bot branch, with a lease on the push; the committed manifest no longer records the destination's own revision, so a merged documentation PR cannot trigger another; tokens reach git and `gh` only through the environment and never through arguments or disk; AI runs are excluded from CI (ADR-023) | Reviewable, idempotent, loop-free publication that can be tested without GitHub |
| D39 | Quality is measured by `python -m repodocs.golden` against hand-authored golden cases named by semantic selectors; types a case mentions are enumerated completely; ratios are null when undefined; evidence is checked against files on disk; AI comparisons replay a recorded response; an exact baseline is enforced by pytest; golden files are never rewritten from output (ADR-024) | Prevents a circular oracle and makes every metric change a reviewed diff |
| D40 | Scanning never runs programs a repository configures: git runs with fsmonitor, hooks, and every filter command disabled, submodules are inspected recursively with the same hardening, a snapshot is the exact commit only when no submodule, ignored analyzed file, or other content differs from it, and an unreadable git state stops the scan. Text from analyzed source is written as escaped text or fenced code spans, Mermaid labels use Mermaid entities, `validate` rejects active Markdown and Mermaid directives, loopback AI requests ignore proxies, neither provider follows a redirect, and redaction rules are version 1.1 (ADR-025) | Repositories are untrusted, and generated output is published for review |
| D41 | Architecture discovery (epic #47) is a separate, optional path: a bounded, redacted source-excerpt context bundle under its own consent (`ai.source_excerpts_consent`, never implied by IR-only consent) and a schema-validated, versioned, inferred architecture view that drives separate diagram files. A view is `proposed` or `inferred`, never `observed`, and never changes the IR, candidates, or confirmations; cross-repository connections stay unconfirmed unless a confirmed candidate is bound to that connection (same direction; its observed request and endpoint evidence files are member files of the two components, and both sides are cited; matching repository pairs is never enough). A view and its context are stored as one transition, a clean clone with no stored view keeps published architecture files as unverified rather than deleting them, and discovery is `complete` only on an explicit valid completion. It amends the no-source-text part of D35 and the AI-cannot-change-diagrams part of D36 for this path only (ADR-026) | Explains applications without a framework adapter without widening what the IR-only AI path may send or letting a model create authority |

## Local web-first implementation contract (review in #64)

| ID | Decision | Rationale |
|---|---|---|
| D42 | The Ollama provider supports authenticated chat completions for hosts ending in `/v1`. Remote gateways require HTTPS and external consent. The Bearer token comes from `REPODOCS_OLLAMA_API_KEY`, read only when the CLI explicitly selects the environment credential source; other callers send no key and refuse remote gateways. Redirects are disabled. Both transports enforce the 512 KiB response limit, send the configured output cap, and share context admission and usage receipts (ADR-020, ADR-031). Gateway completions require one assistant message with a `stop` finish reason and JSON-object text | Lets a private gateway serve the consent-gated Ollama workflow |
| D43 | Owner-approved local/self-hosted web first; public hosting and videos deferred. ADR-027 specifies React/TypeScript with Vite and an optional thin FastAPI/Uvicorn adapter over the shared Python service, polling, bounded single-process jobs, versioned local metadata, ephemeral credentials and explicit restart/cancellation states. The CLI requires no backend. Technical contracts and release thresholds are submitted for review in #64; runtime implementation follows in #65-77. | Deliver a useful browser workflow without a duplicate engine, funded service or speculative distributed infrastructure |
| D44 | Architecture-view claims carry a computed `support` (`supported`, `unverified`, `unsupported`) and reason codes, separate from member-citation `classification` (ADR-028). Support comes only from deterministic facts: a direction-bound observed request/endpoint pair, observed role facts, or a bound confirmed candidate. Names never decide a role. Unsupported claims stay in the stored view and evidence map and are left out of default diagrams; unverified claims are marked; no label says verified. A resolving citation alone never yields `supported`, and human source review and the #54 gate remain required | Valid citation IDs showed a well-formed view, not a true one |
| D45 | Architecture-discovery context selection (ADR-029) ranks substantive source by role and size, spreads the first round across repositories and across backend, frontend and storage files by name and location, picks a block-aligned span of a long file, and counts the inventory, a compact static-import reference index, diagnostics and an instruction reserve against `max_context_bytes`. The index covers literal imports on the excerpted lines of opened JavaScript, TypeScript, Python and Java files only and records no runtime order; targets are `read`, `excerpted`, `unopened` or `unresolved`. Sizes are measured as sent, the omission list yields first when space runs out, and a stored view keeps the exact context its proposal came from. Missing layers, unopened priority files and omissions are reported. Consent, disclosure ceilings, deny list, redaction and actual-read bounds are unchanged; selection version 1.1 invalidates views stored from 1.0 contexts | Makes the bounded context show behavior across subsystems and repositories, and makes omissions and the real total size explicit, without reading or claiming more than before |
| D46 | The CLI and in-process adapters share `repodocs.service` (ADR-030): frozen requests, versioned `WorkflowResult` with distinct run (`complete`, `partial`, `failed`, `cancelled`) and view (`missing`, `current`, `stale`, `invalid`) states, cooperative cancellation and progress hooks, and a per-run `Provider` object instead of environment credentials. CLI JSON and exit codes are unchanged; only discovery contacts a provider | One implementation for CLI and browser without a server, a duplicate engine or shared credential state |
| D47 | Model usage is bounded per run (#67, ADR-031): the complete serialized request is preflighted against the configured context window including its reserved output, using provider token counting after consent where supported or a labeled one-token-per-byte bound; token-count requests have their own bounded, recorded allowance; every generation request, retry and repair reserves its worst-case tokens and cost in one run ledger owned by the shared service and is refused before sending when it would pass an aggregate token, request (ceiling 6, as ADR-026) or cost cap; reported usage over a cap stops the run and is never a complete success; a stop is final; unknown or partial usage stays reserved, never zero; limits only lower hard ceilings, including a run's own limits; rates come only from a project-supplied versioned profile bound to one provider and model, and an unlisted served model is unpriced; output caps and effort are explicit, SDK retries are off, no model is substituted and no server-side fallback is requested; capped or unfinished output is incomplete; a local receipt (`.repodocs/receipts`) records usage and the stop reason. Native Ollama receives its window explicitly, defaulting to 4,096. For Ollama /v1 the window is an admission limit and the gateway model must be configured to match | Makes the analysis bill bounded and honest without a hosted database, quotas or an unverified price table |
| D48 | A native `openai` provider (ADR-032) calls the Responses API with the standard library: explicit model, strict JSON-schema output, explicit output cap and optional effort, `store: false`, HTTPS except loopback tests, no redirects, retries or model fallback, bounded responses and sanitized errors; only one completed assistant JSON output is accepted. Credentials come from `OPENAI_API_KEY` or a per-run in-memory credential, never configuration. Usage maps cached and cache-written tokens out of the input total and keeps reasoning inside output; requests are counted with `/responses/input_tokens` by the run ledger only; changing provider, model or endpoint revokes disclosure consent unless it is given again | Lets users compare an OpenAI model through the same bounded, consented and budgeted engine without a new dependency or the private gateway of #62 |
| D49 | Local web access is a pure-Python in-memory boundary: loopback by default, non-loopback only with an explicit HTTPS origin and a long auth token; exact Host/Origin, fetch-site, expiring bounded session and CSRF checks run before any job is revealed or started; provider keys are per-request in-memory `Secret`s owned by one session and never returned or persisted; consent receipts bind kind (external and source excerpts separate), provider, host, model, policy and preview hash, and a gate re-checks them before every model, token-count and retry request (ADR-033, #71) | Prevents unrelated sites from launching paid or source-disclosing jobs and keeps credentials and consent from widening silently |
| D50 | Web workspaces are backend-created directories under a store root holding the project config, a backend-owned documentation destination and fetched checkouts. Local sources are allowlisted roots chosen by opaque configured name and read in place; public GitHub sources are canonical owner/repo at an exact lowercase SHA, bounded first by a fixed unauthenticated `api.github.com` tree listing (not truncated; entry, file, size and path limits; symlinks and submodules refused) and then fetched by hardened depth-1 Git under a deadline and disk monitor; pins and cleanliness are verified through the snapshot code, and cleanup deletes only marker-owned directories; a pasted public github.com URL is first resolved server-side to its default-branch head SHA through fixed API URLs, and only that SHA is acquired (ADR-034, #96) | Bounds source bytes before download, keeps browser input free of paths and URLs, preserves local work and reuses existing provenance |
| D51 | Project one validated view into deterministic, identity-bound overview/detail Mermaid files; slice oversized groups into at most ten focal nodes with bounded boundary context, preserve evidence and uncertainty, and emit an owned diagram index (ADR-035, #74) | Makes diagram scope inspectable without extra inference or invented relationships; source and intended-user review remain required |

| D52 | The local HTTP adapter (ADR-036, #72) is `repodocs.web.app` (FastAPI, optional `web` extra) over the framework-free `repodocs.web.jobs`, which calls only `repodocs.service`. Routes authorize first, bound request bodies, return a stable error envelope and never send CORS headers. Jobs are polled with a monotonic `sequence` through `queued`, `preflight` (scan and context check, no provider request) and `running`; one runs per workspace and one more may queue, within global active and queue bounds. Idempotency covers the normalized request, not credential handles. An architecture job needs the workspace's current preview hash, a live provider session and a `RunGate`; the service takes consent from that gate for the run only and sends every model and token-count request through it inside the ledger. `max_total_tokens` caps prompt and output together. Records are atomic metadata without credentials; on restart unfinished jobs become `interrupted` and nothing is resumed. Artifacts are served only by recorded name, as regular files whose bytes and manifest entry still match | Exposes one bounded, cancellable, restart-safe job API over the CLI's engine without a second implementation, a broker or persisted credentials and consent |
| D53 | The browser UI (#73, ADR-037) is React 18 / TypeScript 5 / Vite 5 built to `frontend/dist` and served as static files from the FastAPI origin. Provider keys are transient form input cleared after each request and never stored. The idempotency key is generated client-side once per workflow page mount so refresh does not silently resubmit. Partial, stale, failed and budget-exhausted results carry a visible "not current" notice. The `frontend-build` CI job verifies the TypeScript build on every pull request. The CLI and Python tests have no Node.js dependency. | Delivers the browser workflow without CORS headers, without a second server, and without persisted keys; keeps the frontend build separate from and independent of the Python test matrix |
| D54 | The interactive viewer (#75, ADR-038) renders `.mmd` artifacts with `mermaid` (`securityLevel: 'strict'`, DOMParser SVG insertion, no `dangerouslySetInnerHTML`), pan/zoom via CSS transform, scope switching over `job.result.artifact_ids`, evidence display from diagram comments and optional view JSON with allowlisted pinned-GitHub or `<source:name>` links only, and direct API downloads with `Content-Disposition: attachment`. The page CSP allows `style-src 'self' 'unsafe-inline'` only so Mermaid's SVG styles apply; scripts, objects and other origins stay blocked (#93) | Keeps rendering safe against untrusted repository text, prevents path leakage, and reuses backend manifest verification without duplicating diagram modeling in JavaScript |
| D55 | Repeatable local/self-hosted web installation (#76, ADR-039) exposes `repodocs-web` (`repodocs.web.server:main`), `/health` and `/ready` endpoints without leaking credentials or paths, and bounded marker-verified cleanup (`repodocs.web.cleanup.cleanup_workspaces`) skipping symlinks and active jobs. Auth tokens for non-loopback exposure are read via `--auth-token-env`. Static assets resolve from packaged `repodocs/web/static` or `frontend/dist`. | Gives operators a reproducible startup and retention workflow on Linux and Windows while keeping `repodocs` CLI independent of web dependencies |
| D56 | An optional web-only SQLite store (`repodocs.web.store`, ADR-040, #95) under the store root keeps local profiles, hashed session authenticators, workspace ownership and a job mirror; job and artifact files stay authoritative. Keys, raw cookies, CSRF and auth tokens and consent receipts are never stored, and provider sessions and consent stay in memory. A profile is reachable only through a recorded, rotated session cookie (loopback 30 days sliding, exposed 8 hours behind the auth token); logout revokes the profile's sessions; pre-store and mismatched records are adopted by no one; a corrupt or newer store fails closed; nothing resumes inference on restart. The CLI and Actions need no database | Lets legitimate local users keep their saved work across restarts without a database server, persisted credentials or widened consent |

## Change process
When a major choice is finalized, add an ADR in `docs/adr/` with context, alternatives, decision, consequences, and date. Update this table. Never silently promote open decisions to accepted.
